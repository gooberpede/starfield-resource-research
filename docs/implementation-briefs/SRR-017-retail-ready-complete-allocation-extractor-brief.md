# SRR-017 — Retail Readiness for Complete Planet → Biome → Resource Extraction

**Implementation and qualification brief for Codex — OFFLINE ONLY.**

## Decision and objective

Prepare the accepted SRR-016 whole-store reader for **one separately authorized retail Starfield title-card extraction**. Complete the engineering, disposable qualification, provenance, independent challenge, and proposed run card **up to but not including live authorization**. The intended eventual live result is an **actual, reusable, complete Planet → Biome → Resource dataset** from the authenticated game's retained allocation database, with identities and all seven slots preserved so it can subsequently be compared with the independent reproducer oracle. A count-only census, four-sample demonstration, or unjoinable raw-ID inventory is **not** the requested deliverable.

A fully qualified reproducer comparison **is not required for this stage or for the initial extraction**. The goal is to capture sufficient complete, identity-resolved native evidence that the comparison can be developed and performed **offline afterward without another game run merely to obtain omitted data**. Do not let the currently conditional expected-population ledger or four-owner-slot projections prevent implementation of a useful native extract. Do not silently interpret a structural census as an oracle match.

Use the now-committed SRR-016 research baseline and these authoritative documents: `docs/SRR-016-whole-store-census.md`, `docs/SRR-016-native.md`, `docs/SRR-016-interchange.md`, `docs/SRR-016-oracle.md`, `docs/SRR-016-title-census-run-card.md`, `docs/SRR-015-native-extraction.md`, `docs/SRR-015-oracle-comparison.md`, `docs/SRR-013-retail-title-paired-structural-observation.md`, `docs/SRR-013-structural-title-run-card.md`, and `docs/research-workflow.md`. Resolve version changes against the current repository; do not silently copy stale counts or identities from an earlier handoff.

Retail target remains the pinned `Starfield.exe` **1.16.244.0**, SHA-256 `7e9adb1414a8e1b325e5e1f097b9b17b78deb7eebeda37a333351a43a60f9d28`, unless explicit separate approval changes it. The source data of interest comes principally from `Starfield.esm` and `ShatteredSpace.esm`. ## 1. Establish the extraction's scientific and output contract

The extraction starts from the authenticated published `BSComponentDB2::DB` `+0x300` tree, walks **every root-reachable mixed descriptor** without prefiltering by a reproducer planet list, discriminates every registered `CTPerBiomeData` target, and preserves all seven native u32 resource slots in native offset order. Keep **present-but-zero** records; do not convert absent records to zeros. Account separately for all mixed descriptors, target descriptors, excluded mixed records, refusals, ambiguous identities and complete traversal coverage. The target population is the **entire reachable admitted store at the observed checkpoint**, not all imaginable records, queued commands, unlinked allocations or other indexes.

The final usable dataset must represent **Planet (PNDT) → Biome (BIOM) → Resource slots** with, for every qualified row:

- Stable source identity of planet and biome, at least defining plugin plus local record ID, **alongside the observed 32-bit runtime FormIDs** and original raw index keys;
- All seven original resource words, their ordinal and field/role, including explicit zero/null lanes; for nonzero values, the resolved source identity (plugin/local record ID) and independently validated native `BGSResource` identity;
- Any native typed input identities needed to interpret the record (including RSGD where present), observed metadata and defensible provenance; distinguishing observed values from inferred/reproducer values;
- Exact count and qualification metadata, pinned game/source versions, checkpoint, process-epoch identity in private evidence, extraction algorithm/manifest identities, paired-read verdicts and explicit unresolved/refusal records.

Provide **a deterministic machine-readable export** (e.g. versioned JSON and/or normalized CSV) and a straightforward human-readable planet/biome/resource view or documented transformation. Define the canonical key order and duplicate policy. Keep raw native evidence separately under approved private custody; a cleaned shareable export must omit live addresses, private paths, secrets and other unnecessary process details. Define how normalization failures are reported **without dropping raw rows or silently claiming a complete comparable dataset**. The complete useful export must be reproducible from the sealed acquisition evidence. Supply an offline demonstration that its output is consumable by the existing SRR-016 comparator or a deterministic interchange adapter; do not implement new oracle rules solely to make this pass.

## 2. Resolve the actual FormID identity correspondence

Start with the simplest testable explanation: the game's records and the reproducer are based on `Starfield.esm` and `ShatteredSpace.esm`. Identify exactly how the *actual process* expresses PNDT, BIOM, RSGD and resource IDs from those ESMs, including load-order namespace prefixes or alternate FormID sizes **only if supported by native evidence**. Do not assume that all runtime FormIDs always equal on-disk 32-bit FormIDs; equally do not assume elaborate remapping is needed for the base-game identities already validated in SRR-013.

Trace native load-order/FormID assignment methods and upstream callers as needed; test specific independently sourced records from both ESMs where present and available. Establish what the high bits mean and how a source plugin and local record ID are recovered for **all IDs actually needed by the census**. Account for relevant extra plugins only when their presence or records matter to the observed population. If the runtime namespace table is readable, prefer a read-only, epoch-bound native witness; otherwise propose and validate a defensible independent mapping using the effective loaded inputs. Check that it is one-to-one, collision-free and internally consistent with native FormID lookup and type witnesses. The expected ledger is neither an oracle for identity resolution nor a substitute for independent process binding.

Do not confuse a Bethesda reference record's FormID with a memory pointer/handle. Consider a different identifier class only on specific evidence contradicting PNDT/BIOM/IRES interpretation. Clearly state what, if anything, would make a whole-population normalized export unqualified. If that identity problem proves genuinely blocked offline, give a concrete blocked-lead report and **do not recommend authorizing an unjoinable count-only live attempt as though it met this brief**.

## 3. Retail acquisition, work envelope and protection

Adapt, do not replace, the tested SRR-013/SRR-016 least-rights read-only access and native-layout parser. Qualify the **exact intended retail command**, admissible source manifest, Steam launch/process attribution, creation epoch, executable/mapped-image identity, publication and registration checks, operator-held **responsive title-card** marker, and unique one-use authorization/custody binding on owned disposable processes. SRR-013's consumed authorizations cannot be reused. No debugger, process suspension, memory write, injection or privilege escalation.

Establish a population-scale acquisition envelope from the SRR-016 measured fixtures, native maximum geometry and any justified bounded retail static capacity evidence. Cover both complete independent collections; tree windows/levels/nodes, mixed records, typed entries, form table capacity and chain lengths, input lists, queries/reads/bytes, journal/output bytes, identity and closeout operations. Include margin justified by the likely real store, **not arbitrary timing deadlines**. Require finite, fail-closed work limits and cooperative cancellation, but **no arbitrary wall-clock cutoff**. Test the actual retail-facing backend on disposable fixtures including exceeding the proposed bounds. Document what happens when the real population exceeds a cap: preserve incomplete private evidence, report truthful insufficiency and seek separate approval for a changed candidate; no automatic retries or raising limits live.

Retain SRR-016's no-skip rooted traversal, complete native identity validation, end fences/count reconciliation, independent FormID-map lookup, typed witness checks, two fresh-root complete reads separated by at least 25 ms, consumed-window/epoch rechecks and sealed replay. Maintain distinct structural, typed-input and value agreement verdicts; reject identity drift and conflicting metadata. A successful paired extraction is not an atomic snapshot, proof of uninterrupted component lifetime, proof of a writer invocation, or proof that no other store exists. An all-zero valid record is **present**.

Review and carry forward the established preflight/postflight protections from the SRR-013 title-card experiment: normal non-elevated Steam environment, disabled Steam Cloud and overlays as required, no inherited compatibility flags, backup/preservation checks of the **98 Documents and 95 Steam remote protected save pairs and both designations**, zero unexplained new entries, and adequate C:/D: reserve. Keep the real operator responsible for all UI interactions and normal Quit. No save selection or travel is needed at the title card. The final run card must pin the exact preservation and independent exit-witness procedure. These requirements are to be **tested or prepared offline only in this phase**, never performed against the live game under this brief.

## 4. Independent qualification and challenge

Demonstrate the actual export, not merely counts, using owned native-shaped fixture processes and separately constructed reference truth. The test inventory must include:

- At least the existing 3,600 mixed/3,210 typed corpus-shaped and 5,120 mixed/4,096 typed fixtures, multi-level and direct-root trees, mixed types, empty store, unexpectedly present owners, zero/all-seven populated slots and duplicates;
- Source/retail FormID correspondences from both ESMs where applicable, nonzero loaded plugin prefixes, invalid/missing/ambiguous namespace entries, canonical collisions, wrong PNDT/BIOM/RSGD/resource types, wrong resource vptr and indistinguishable-key attempts;
- Tree corruption, linked-list/fence/extent disagreement, count mismatch, partial read, region crossing, FormID-map collision/chain corruption, population overrun and evidence budget exhaustion;
- Paired slot disagreement, typed-input/BIOM identity changes, mutation/ABA cases, incomplete second pass, cancellation and receipt/replay tampering;
- Round-trip equivalence of sealed native observation → normalized Planet/Biome/Resource export → comparator-compatible input, with independent assertion of *all* keys and seven words, including zeros and exceptional rows;
- Original SRR-013 and SRR-016 disposable regression suites and sibling reproducer validation, where available. Do not require inaccessible historical retail journals or imply that previously reported retail verdicts were requalified if their custody is inaccessible.

The independent challenger should create at least some byte-level and identity-mapping counterexamples **independent of the production fixture builder**. Assess prose/pseudocode/diagrams against implementation and native evidence. Verify input separation: reproducer predictions must never select which native records to read or alter the recorded native result. Confirm that no actual retail access occurred.
