# SRR-002 — Retail planetary-resource allocation: static reconnaissance

## Assignment and controlling question

Work in `starfield-resource-research`. Investigate the **pinned retail `Starfield.exe`** to identify and critically qualify native-code candidates for the planetary/biome-level **inorganic resource-allocation machinery** recovered in the Creation Kit (CK). The controlling question is:

> Which retail native functions or connected code regions, if any, can be supported as candidates or established static correspondences to the CK's planetary/biome resource-allocation machinery, and what does the available static evidence establish about their roles and relationships?

This is an **investigation**, not a predetermined function-matching exercise. Pursue credible alternative leads and falsifications. A useful negative result is acceptable when supported by a defensible bounded search; failure to find an exact CK counterpart is not, by itself, proof of absence. The deliverable must provide a substantive answer or a justified BLOCKED disposition—not merely a list of searches performed. The **retail native runtime path, full algorithmic equivalence, and generation/cache lifecycle are not required to be proved in SRR-002**.

Maintain the boundary with `starfield-outpost-research`: biome-level resource *eligibility/allocation* is the subject; landing-site raster masks, deposit contours, source-map construction, outpost geometry, and extractor placement are outside scope except where a narrowly identified consumer is useful as a lead.

## Investigative freedom and candidate evidence

Select and sequence bounded static tests by information gain. Useful **leads, not mandatory assumptions**, include the CK orchestration, per-biome generation, Special/Common selector, descendant helper, guarded fallback, MT19937 draw/probability conversion, biome shuffle, and the distinctive **five-family** and **eight-resource** guards. The CK static and live function register can guide signatures and graph comparisons, but CK virtual addresses cannot be transferred to the retail image. Constants `5` and `8`, MT-family code, generic weighted selectors, and a Ghidra-generated `FUN_...` name are common enough to produce false positives; do not equate an isolated match with a resource-generation role. Conversely, compiler/inlining/version differences may hide a genuine correspondence.

For promising candidates, seek discriminating **combinations** of instruction/data-flow features, call or caller relationships, resource-record use, RNG consumption, branch ordering, state updates, and independently supported connections. Compare machine-code/instruction evidence where possible; qualify decompiler inference separately. Record mismatches, negative controls, ambiguous matches, search limits/truncation and alternatives. Preserve the distinction between:

1. **CANDIDATE** — limited similarities; materially plausible alternatives remain;
2. **STRONG CORRESPONDENCE** — several distinctive features and relationships corroborate the match, with explicit remaining gaps;
3. **STATICALLY ESTABLISHED** — the identified retail implementation and relevant static relationships are demonstrably present in the pinned image, within defined bounds;
4. **RUNTIME CONFIRMED** — reserved for separate live execution evidence; **not achievable by static-only SRR-002**.

Use these mapping terms alongside, not instead of, the repository's `PROVEN`, `STRONG`, `PROVISIONAL`, `COUNTERFACTUAL`, and `SUPERSEDED` evidence labels. Do not claim that code executes in ordinary gameplay or determines observable biome membership merely because a static correspondence exists.

## Execution limits

Permitted: read-only Ghidra inspection, existing analysis exports, bounded offline comparison scripts, source/documentation updates within this brief, and review of public/maintainer-owned prior work. Tool execution must preserve project/database integrity; confirm read-only/no-analysis flags **and** pre/post identity of protected database files where relevant. Keep output sizes, traversal scope and timeouts inspectable, and record partial/error returns. Avoid uncontrolled whole-program decompilation or explosive graph expansion.

**Not authorized:** launch the game or CK; attach a debugger; hook/inject code; alter executable bytes, installed game files or saves; make changes to Ghidra symbols, function boundaries, types, comments, analysis state or database; import/reanalyze without a separately approved setup; change the reproducer's model or data; copy large outpost tooling trees; stage, commit, push, tag or publish; or contact/upload to outside services. Stop only the affected action on a genuine blocker, preserve useful completed work and identify the minimum authority/input needed. Purely read-only follow-up work may continue where independent of the blocker.

## Independent challenger and completion protocol

Invoke **one independent reviewer sub-agent at a time**, after the investigator's own implementation phase. Give the challenger this original brief, candidate dossier, exact proposed diff, relevant primary instruction/call/data evidence, unsuccessful leads, verification receipts, and access to the preserved starting state. Require the reviewer to **actively challenge** function identifications, common-constant/RNG false positives, missing alternatives, incomplete search coverage, executable/database mismatch, unqualified runtime claims, evidence/publication holds and every acceptance criterion. A reviewer who only agrees with the agent's summary has not performed the review.

A reviewer disposition of **REWORK** returns the same assignment to Codex for correction and renewed independent challenge until COMPLETE or genuinely BLOCKED; do not substitute an agent's declaration of COMPLETE for the gate. A bounded, well-tested negative result can be COMPLETE if it answers the frozen scoped question to the stated coverage; an unfinished search with promising authorized leads is INCOMPLETE/REWORK. **BLOCKED** requires a demonstrated essential dependency, safety restriction or lack of authority, with attempted alternatives and minimal next action. The challenger writes detailed rounds locally; the dossier retains the final disposition, immutable reviewed-content manifest/commit identity, material scientific corrections or objections, and evidence limitations. On an uncommitted handoff, use the SRR-001 review-status-block exclusion and final-patch replay method. Renew the review after substantive changes.
