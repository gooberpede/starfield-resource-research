# SRR-001 — Executable identity and research foundations

## Assignment

Work in the existing `starfield-resource-research` checkout. Establish what can be verified about the historical Creation Kit (CK) research, record the identity of the installed retail executable if accessible, and put the documentation and review workflow in place for later investigations. Completion qualifies this foundation only. The retail native research question remains open.

Start with the checkout's `AGENTS.md`, `README.md`, `docs/README.md`, `docs/PROVENANCE.md`, `docs/v1-research-baseline.md`, the function register, the CK experiment notes and evidence manifests, and `THIRD_PARTY_NOTICES.md`. Record starting HEAD, index and worktree status, including pre-existing changes. Preserve existing work. Read the maintainer-supplied `ck-about-1.16.244.0.PNG` if available and use only task-relevant local records or maintainer-designated inputs for identity checks. Record source pointers, the checks actually run, and any access limitations.

## 1. Establish separate executable identities

- **Historical CK static evidence.** The About dialog reports `1.16.244.0 [Data: 582]`. The repository records MD5 `0215f03ec24922dfd4015dcdc5317dc4` for the focused Ghidra exports. Keep these as separate observations with their sources. If a candidate CK executable is accessible, read its file and product versions and compute MD5 and SHA-256 without launching or modifying it. Compare its MD5 to the historical record and establish the provenance linking its version metadata to the hashed bytes. A matching candidate supports a version attribution for the fingerprinted exports when the evidence is consistent. Attribute Data 582 to those exports only if a contemporaneous record or a documented link ties the About observation to that candidate. Preserve the original MD5 and the distinction between the historical pin and the new SHA-256 measurement. If the binary is unavailable, the hash differs, or metadata conflicts, retain the recorded fingerprint and describe precisely what remains unresolved. A matching version string alone is insufficient.
- **Historical CK live evidence.** Preserve the existing address-space association and the fact that a separate live executable hash was not recorded. Qualify the live build separately and require trace-specific evidence for any stronger attribution. Preserve the observations, addresses, source files, evidence grades and supersession history.
- **Retail.** For the accessible, designated `Starfield.exe`, record file and product versions, SHA-256, distribution or build identifier if verifiable, observation time in UTC, and a reproducible method for identifying the input without exposing private paths. Record relevant installed data or plugin identities only where a claim depends on them. This is an observed local baseline for future work. Keep the historical retail planetary-scan/holdout build unresolved unless evidence specific to those runs establishes it. An outpost-project pin, matching CK version string, or successful output comparison supplies no retail native mapping.
- **Applicability.** Maintain a compact register in `docs/PROVENANCE.md` or link to one adjacent register if needed. Give each row an evidence or claim pointer, executable/build reference, claim type, qualification and limit. Cover the focused CK static bundles, CK live traces, historical holdout outputs, the canonical 1,444-body validation, and the current retail identity observation. Distinguish output semantics, native control flow, addresses/offsets and lifecycle claims. Keep historical data/plugin and retail versions explicitly unknown wherever unrecorded. Keep executable builds distinct from project release versions.

Record one identity outcome per check, with supporting sources and the evidence required to resolve any gap. Try relevant, authorized sources before accepting an unknown. Missing historical proof can satisfy this brief when explicitly qualified. If a current retail executable cannot be read, complete the available work, record the exact blocker and the minimum input needed, and leave the retail identity criterion blocked. A verified retail baseline is required before later retail research begins.

## 2. Add the documentation and operating workflow

- **One principal dossier per bounded investigation.** Add and index a compact SRR-001 dossier under `docs/` with objective, scope, baseline, method, observations, interpretation, limitations, evidence links, verification and review status. Use it as the first example. Reuse `docs/PROVENANCE.md` for executable identities and the applicability register. Link to existing v1 findings and evidence instead of copying them. Add a concise workflow section to `AGENTS.md` or one linked workflow page, using a single controlling home for each rule. Update the documentation index and any reader-facing build qualification that would otherwise be ambiguous. Keep historical evidence files and experiment reports byte-for-byte intact and qualify them through the provenance and navigation layer.
- **Local layout and retention.** Use `.local-work/codex/SRR-001/` for working notes, task inputs and receipts, `.local-work/independent-review/SRR-001/` for review rounds, and `.local-work/diffs/` for the review patch. Confirm Git ignores the locations and that they contain no tracked files. Retain selected research evidence deliberately, with identity, provenance, scientific purpose and a named consumer. Scratch files and review copies do not acquire protected status by being created or read. Preserve existing local material and record promotion decisions only where needed.
- **Verification follows dependencies.** Identify the task's protected primary inputs and retained outputs it actually consumes. Verify their content identities at relevant boundaries with cryptographic hashes or pinned Git objects where appropriate. Use the historical MD5 for reconciliation and SHA-256 for newly pinned file identities. Recheck relevant protected inputs after work and compare the preserved tracked paths against the starting state. For future intentionally mutable inputs, specify the starting identity and expected transition in the relevant brief. Test content equality by content. Require matching timestamps only where the brief makes metadata part of the experimental condition. Skip unrelated historical inventories and routine full-tree rehashing.
- **Space guard.** Before an operation capable of materially consuming disk space, measure caller-available bytes on **both C: and D:** and check that expected writes, temporary copies and output growth leave at least **40 GB (40,000,000,000 bytes) free on each drive**. For a sustained writer, check during execution and before each material write stage, allowing time to stop before crossing the floor. Refuse or stop that operation if the floor cannot be maintained or either reading is unavailable. Preserve inputs and any useful partial output, and record the affected drive and next safe step. This is a free-space floor, with no fixed size cap on `.local-work/`. Record a read-only measurement and demonstrate the decision rule with dry-run inputs covering both drives, insufficient projected headroom, and a missing reading. Lightweight documentation work and read-only identity checks may continue if a material write is blocked. No new guard framework is required for this phase.
- **Publication independence.** Include a small claim-level release scope table in the dossier or existing provenance register. For each candidate claim, identify its build applicability, essential evidence, public verification route and any hold. A reader starting from the public repository and any explicitly named versioned public dependencies or lawfully obtained inputs must be able to follow the method and inspect the basis for an in-scope claim without `.local-work/`. Walk one existing CK claim through that route. Mark a missing essential source, unresolved identity, or unclear redistribution right as a hold on the affected claim. Keep future release numbering, tagging and publication for a later maintainer decision.
- **Permissions and credit.** Document the basis for inspection/use and, separately, any redistribution clearance. Identify third-party sources and explicitly credit substantive contributions where known, using `THIRD_PARTY_NOTICES.md` and relevant dossier references. Hold material with unclear rights or privacy exposure. Respect the letter and intent of permissions and treat any research exception as specific to its material and purpose. Exclude unauthorized third-party content, proprietary payloads and means to reconstruct proprietary material from publication. Existing access, attribution and a public URL alone grant no redistribution permission. Preserve the CK screenshot locally if supplied and record the observed text and its provenance. Publishing the image is outside this brief.

## 3. Run independent review before handoff

Spawn one independent challenger sub-agent at a time. Give it this original brief and AC1–AC7, the starting state, proposed deliverables, actual diff and file inventory, and direct access to relevant primary records and check results within existing permissions. The reviewer independently checks each criterion with evidence and challenges the strongest conclusion and its most plausible counterexample. In particular, have it test whether the CK screenshot was overinterpreted, whether a current build was assigned to a historical run, whether a retail mapping was implied by outputs, whether preserved evidence changed, and whether a release candidate still depends on disposable local files. The reviewer may write its review record and leaves the implementation to Codex.

- **COMPLETE** requires every mandatory criterion to pass on the final substantive snapshot. An explicitly qualified historical unknown may pass AC2.
- **REWORK** identifies a remediable gap against the original criteria. Codex corrects it within the same assignment, verifies the change and returns the revised snapshot for independent review. Repeat until COMPLETE or an evidenced BLOCKED. Keep prior review rounds locally.
- **BLOCKED** identifies a mandatory unmet condition that cannot be resolved within available authority or resources, with attempted checks, completed work, and the minimum action needed to resume. If an independent sub-agent is unavailable, preserve the handoff and report the review gate as blocked. Self-review cannot satisfy the gate.

The tracked dossier records the final disposition, reviewer role, immutable identity of the reviewed material and material limitations. Use a commit ID if available or a SHA-256 of a deterministic manifest covering the reviewed paths and their exact contents. For this uncommitted delivery, the dossier's review-status block is excluded from the manifest it cites. State the exclusion, then have the reviewer verify the populated block and confirm that all covered content still matches. Any later substantive change requires renewed review. Preserve scientific corrections and unresolved material objections in the durable research record. Detailed round notes and administrative receipts stay local. Describe this as an internal challenge against the brief, with scientific confidence grounded in the underlying evidence.

## Acceptance criteria

| --- | --- |

The register separates the current retail pin, historical output checks and CK native claims, with unknowns and limits explicit. |
| AC3 — Documentation and local layout | The index links to one SRR-001 dossier, the applicability register and controlling workflow. Changed relative links resolve, text is valid UTF-8, and the three local locations are ignored and untracked. |
| AC4 — Proportionate verification and space guard | The local receipt identifies actual dependencies, scope and content checks. The documented rule accepts equal content with incidental timestamp changes. A table-top or dry-run check demonstrates allow at the floor after projected writes, refuse when either drive would fall below it, and refuse when either reading is unavailable. Use simulated values for low-space cases. |
| AC5 — Publication and attribution | The compact scope table names evidence, a public verification route or explicit hold, and rights and credit status. The reviewer can walk the selected CK claim using the documented public sources or verify the stated hold. No new local-only dependency, sensitive path or restricted material enters the proposed tracked text. |
| AC6 — Reviewable handoff | Export a task-only patch in `.local-work/diffs/` that includes all new and changed task text, including the completed review-status block. Use Git's native output per `AGENTS.md`. Check the patch against the recorded baseline in an isolated context and compare resulting file contents with the delivered files. Account for pre-existing edits separately. |
| AC7 — Independent disposition | A separate reviewer cites evidence for every criterion, exercises the challenge above, and verifies corrections against the final snapshot. The detailed review is local and the dossier carries the checked disposition, snapshot identity and material limitations. |

Return the disposition, the dossier and provenance paths, the patch and local review locations, a short criterion-by-criterion result, and unresolved identity or publication holds. Record the actual verification performed. A blocked handoff identifies the unfinished criterion and retains the completed work.

## Non-goals

- Native analysis or experimentation of either executable, including disassembly, debugger work, Ghidra import, instrumentation, live gameplay, address relocation or equivalence testing. Executable identity work is limited to read-only metadata and hashing.
- Changes to the v1 algorithm, the sibling reproducer, datasets, installed tools or game files. No protected evidence edits, bulk migration, deletion, or repository-wide evidence census.
- Staging, commits, pushes, tags, release creation, repository visibility changes, external uploads, or publication. Follow the environment's permissions for local reads and writes.
