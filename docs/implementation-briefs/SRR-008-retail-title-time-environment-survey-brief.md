# SRR-008 — Retail title-time environment survey

## Authority and controlling question

The maintainer **explicitly authorizes one live launch of Starfield through `steam://rungameid/1716740`** for this bounded, read-only environment survey. This authorization is **not** permission to attach a debugger, arm breakpoints, deploy an observer/SFSE plugin, load a save, modify game files or settings, manipulate the UI, or perform the later allocator experiment.

**Controlling question:** Can the actual Steam-launched Starfield process be identified and its title-time native module environment inventoried with sufficient integrity and provenance to prepare a separately reviewed retail debugger-admission configuration?

Read `AGENTS.md`, `docs/research-workflow.md`, `docs/PROVENANCE.md`, the SRR-005–007 dossiers, `docs/SAVE_PROTECTION.md` in the maintainer-owned outpost project as relevant, and this brief. Existing SRR-006/007 native tooling and retained identities are prior evidence, not authority to operate it against Starfield. Preserve historical findings and earlier review identities. Record starting HEAD, index, worktree status and exact scoped dependencies; do not disturb unrelated work.

## 2. Authorized live sequence — exactly one session

1. **Launch:** Codex invokes the known working Steam URI `steam://rungameid/1716740`. A successful URI invocation, Steam handler PID or shell return does **not** identify the retail target process. Locate and validate the actual `Starfield.exe` instance without attaching a debugger or controlling its threads. Retain a query/synchronize handle bound to the exact process; record PID, process creation FILETIME/epoch, full executable path, file identity, architecture, Windows version, product/file version and backing executable SHA-256. Verify identity before attributing any module observations. A process replacement or handoff requires requalification, not silent adoption of a new PID.
2. **Title barrier:** The game first displays a title card requiring operator input to reach the main menu. **The maintainer, not Codex, confirms the visible title card and its responsiveness.** Codex must not drive the desktop, inject keys, advance the UI or assume a native event corresponds exactly to that visual transition. Mark the operator confirmation and its actual clock source as an observation boundary, not an exact engine timestamp.
3. **Read-only inventory:** While the operator remains at title, collect **two** bounded native module inventories for that same retained process epoch, with actual timestamps. Record for every enumerated module its resolved path where accessible, backing-file identity and hash where safely accessible, mapped base, image extent, relevant PE identity, enumeration and read errors, and any modules present only in one snapshot. Revalidate process identity and epoch before/after each inventory. Hashes of file-backed modules are not proof that mapped bytes are identical: qualify that distinction. Do not require the snapshots to match; classify drift, missing access or unexpected modules, and explain their implications for the future debugger admission profile. A safely observable anomaly should be recorded without terminating the survey reflexively.
4. **Seal evidence:** Conclude scientific collection once both snapshots and necessary identity checks are complete, or record the bounded incompleteness. Flush and seal a versioned local report/manifest with hashes, sequence/timestamps, process/module observations, permission/coverage limits and a final durable prefix. Operator delays, slow loading or quiet intervals **are not automatic timeouts or negative scientific evidence**. Actual identity, storage, access or integrity failures stop only the affected acquisition, while preserving valid earlier observations.
5. **Normal quit:** After the survey is sealed, the maintainer may press the required key to reach the main menu and select **Quit**. Codex observes the exact process's exit through its retained query/synchronize handle, without debugger ownership. Record normal or abnormal exit separately from scientific completion. A crash *after* verified evidence sealing does not invalidate valid pre-exit inventory. **No forced termination, restart, debugger attachment or process injection is authorized.** If the game does not quit, notify the maintainer and request an explicit decision; do not infer termination authority.
6. **Postflight:** Recheck protected saves/backups, relevant configurations, installed-game inputs, output identity and storage protections. Note any new autosave/transient files in the isolated area without rewriting historical originals. The maintainer controls restoration of settings or cloud state after assessing any synchronization conflict. Preserve privacy-sensitive raw paths and metadata locally, not in public documentation.

## 3. Scientific interpretation and outputs

Keep **process identity**, **module-inventory completeness**, **environment qualification**, **operator phase**, **game exit**, and **instrumentation health** as independent findings. Successful title-time inventory does not prove initial startup coverage, game allocator invocation, module permanence, or safe later debugger attachment. An unknown module is not automatically a failure; an unresolvable critical module identity is a hold on the relevant retail admission claim. A single process's two samples cannot establish a universal module set.

Produce **one principal dossier**, `docs/SRR-008-retail-title-time-environment-survey.md`, linked from `docs/README.md`. Include the controlled question, actual environment, authorization, exact methods, source and target pins, operator markers, collected summary, two-snapshot differences, limits, risks, candidate future module approval policy, claim-level publication eligibility and the next bounded engineering action. Retain the complete machine-readable inventory, tool/run receipts, any sensitive paths and detailed independent review under `.local-work/codex/SRR-008/` and `.local-work/independent-review/SRR-008/`; the reviewable patch belongs in `.local-work/diffs/SRR-008.diff`. Promote only minimal, rights-cleared and privacy-reviewed evidence that is essential for the public claim. Update provenance/glossary/function or structure registers **only** where new established facts require it. No extra report proliferation.

If the live survey is blocked before launch, deliver the honest partial dossier and exact missing condition; do not substitute synthetic observations for retail results. No subsequent live retry is authorized automatically.

## 4. Independent challenge and completion

Use a separate challenger sub-agent after integration. Give it the original brief, actual run and tool records, pinned inputs, scientific claims, code/diff and evidence, with permission to test counterexamples. The reviewer must independently verify that the reported executable belongs to the authenticated Steam-launched process and epoch; both inventories refer to that process; module drift/errors are classified conservatively; the operator title marker is not presented as a native timing fact; and neither observed module presence nor absence is overinterpreted. Critically challenge the separation of scientific evidence from post-seal crash/quit outcomes and the absence of any unauthorized debugger/UI/Save2 operations.

**COMPLETE** requires each mandatory criterion below to pass on the final substantive snapshot; a scoped qualified result is acceptable when its original question is actually answered. **REWORK** requires correction of an available remediable gap, with further independent review. **BLOCKED** requires a genuine missing prerequisite/authority/capability, an explicit account of attempted checks and the minimum next action. A failed survey is not a successful experiment, and an unobserved module is not proved absent from all time. The reviewer must not convert a failed criterion into a pass by narrowing the original question after execution.

| ID | Acceptance criterion |
| --- | --- |
| **AC1 — Authority and preservation** | One authorized Steam-URI session only; exact allowed operations and environmental settings recorded; original saves, backups, Git and other protected inputs preserved; no unauthorized process/debugger or desktop actions. |
| **AC2 — Identity** | Target identification binds actual Starfield executable bytes, process handle, PID, creation epoch and mapped-image context; Steam URI handler is not mistaken for game process. Identity ambiguity is explicitly held. |
| **AC3 — Two inventories** | Two timestamped title-time module inventories obtained for the same authenticated process epoch, with bases, extents, backing identity/hashes and explicit inaccessible/drifting modules. Their actual scope and limitations are independently checked. |

| **AC5 — Reproducible and lawful evidence** | Output source/tool version, input hashes, process/module schema, bounded acquisition method, local custody and public verification route/holds recorded; confidential or proprietary payloads not released. |
