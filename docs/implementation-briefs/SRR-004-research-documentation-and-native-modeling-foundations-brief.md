## Required documentation foundations

**1. `docs/glossary.md`.** Create one concise, navigable glossary of terms that actually occur in the research. Define concepts precisely enough for an unfamiliar technical reader; identify official/native names versus research-assigned descriptive terms, aliases, ambiguous usages, and deprecated terminology where relevant. Cover distinctions likely to cause mistakes: planetary/biome resource allocation versus landing-site deposit generation; resource identity, occurrence, Common-family configuration and biome assignment; static reachability versus observed runtime execution; direct call, indirect call, callback receiver, virtual slot and dispatch; form record and form bucket; CK versus retail executable; preferred VA, RVA and runtime VA. Define PNDT, BIOM, RSGD, IRES, ATMO, PE, RTTI, RNG/MT19937 and other abbreviations **without inventing undocumented expansions**. Cross-reference authoritative existing descriptions where beneficial. Avoid boilerplate definitions of every ordinary technical term.

**2. `docs/structure-register.md`.** Introduce one build-qualified native structure/relationship register, rather than a file per object. An entry must state the executable build/hash or link to its pinned provenance, owning context or candidate object, native identifier versus proposed semantic alias, observed offset and unit, access width and operation where established, evidence locator, confidence for **each field or relationship**, and explicit unknowns. Distinguish directly observed memory accesses and vtable entries from hypothesized field meanings, ownership and lifetime; partial layouts are valid and must not masquerade as complete C++ class definitions. Start with a **small evidence-backed selection** relevant to SRR-003's callback receiver/vtable and SRR-002's planet allocation state (such as work-list, RNG, family-cache and shared-ID relationships). Record only fields supported by the existing evidence and needed to clarify these examples; do not attempt an exhaustive native layout census. Keep CK and retail layouts separate and do not transfer offsets between images.

**3. Conventions in `docs/research-workflow.md`.** Add a short controlling section for optional pseudocode, Mermaid diagrams and native-structure records:

- Use pseudocode inside the relevant dossier to communicate established control/data semantics—not copied Ghidra decompilation. Preserve branch conditions, sequencing, early exits, side effects, fallbacks and unknowns. Label invented variable/function names as research aliases; tie nontrivial operations to native evidence. Do not silently substitute the Python reproducer's behavior for unproven retail behavior.
- Prefer text-based Mermaid for **control flow**, **data flow**, and **structure relationships** when a diagram genuinely clarifies more than adjacent prose or a table. Label direct/static edges, conditional or indirect edges, and unresolved links explicitly. Visual styling alone must not encode evidentiary confidence; provide a readable legend or labels. Avoid representing static reachability as observed gameplay execution.
- Require that diagrams be syntactically validated **and rendered/visually inspected** with a documented available method. If a rendering tool is unavailable, record the limitation, perform every available syntax/structural check, and do not claim visual validation. Do not install dependencies or contact external services merely for validation without separate approval.
- Update the glossary or structure register when a newly introduced reusable term/field warrants it, not as a mechanical requirement to create an entry for every address, variable or local observation. Cross-link rather than duplicate long explanations. Keep research findings, editorial conventions and review metadata distinct.
