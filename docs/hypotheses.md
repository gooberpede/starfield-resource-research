# Hypotheses

This file contains working models and unproven explanations.

None of the statements below should be treated as established engine behaviour unless they are later moved to `known-facts.md` with supporting evidence.

## H1 — One ordinary inorganic resource family per biome

### Working hypothesis

A normal biome is assigned at most one of the eight ordinary inorganic resource families.

Under this model, different members of the same family may occur together in one biome, while resources from different families normally require different biomes.

Example:

```text
Nickel + Cobalt
```

may be expected to co-occur because both belong to the Nickel family.

By contrast:

```text
Cobalt + Ionic Liquids
```

should not normally be expected to co-occur because they belong to different families.

### Evidence

Across 1,436 analysed bodies:

```text
FamilyCount <= BiomeCount
```

with zero violations.

A particularly strong subset is:

- 880 one-family / one-biome bodies.

### Important limitation

The aggregate count test does not prove one family per biome.

For example, a body with two biomes and one family could theoretically have:

```text
Biome A: Aluminum + Beryllium
Biome B: Aluminum + Neodymium
```

Status: strongly supported, not proven.

## H2 — Resource-family allocation occurs before member/branch selection

### Working hypothesis

The engine first selects or associates a resource family with a biome, then performs a subsequent deterministic selection within that family's structure.

Conceptually:

```text
planet + biome + seed + generation data
            ↓
      choose family
            ↓
 choose branch/member subset
            ↓
 final biome resources
```

### Motivation

This model naturally explains:

- the family-count/biome-count constraint;
- the repeated appearance of family roots;
- the presence of different subsets of members from the same family;
- skipped intermediate family members.

Status: plausible structural model.

## H3 — The family root is guaranteed rather than independently rolled

### Working hypothesis

Once a family has been selected, the family root is inserted or otherwise guaranteed by the algorithm.

The remaining non-root members are selected separately.

### Evidence

Across 2,064 observed descendant occurrences, there were zero cases where a descendant appeared on a planet without its family root.

### Alternative explanation

The root might instead be generated by a probability or list structure that happens to make it unavoidable.

Static analysis is needed to distinguish explicit root insertion from an equivalent data-driven mechanism.

Status: strongly supported outcome; implementation mechanism unknown.

## H4 — Intermediate family members are selectable rather than mandatory ancestors

### Working hypothesis

The family structure does not mean:

```text
deep member selected
    =>
all ancestors selected
```

Instead, a deeper family member can be selected while intermediate members are skipped.

This behaviour is established at the planet level; the unknown part is the exact runtime selection mechanism.

Status: outcome established, mechanism unknown.

## H5 — RSCS contributes to deterministic selection

### Working hypothesis

The PNDT Resource Creation Seed (`RSCS`) is an input into deterministic resource selection.

It may contribute to:
- family assignment;
- family branch/member selection;
- ordering or effective-level selection;
- or multiple stages.

### Evidence

Prior controlled experiments showed deterministic behaviour for fixed seed/configuration.

The Creation Kit `OnApplySeed` path reaches selection machinery.

### Caution

It has not been proven that RSCS directly seeds a conventional PRNG.

Earlier Ghidra work suggested an RSCS-derived value may instead enter generic leveled-list evaluation as an effective level or comparable selector.

Status: involvement strongly supported; exact semantics unresolved.

## H6 — RSGD defines the possibility space, not necessarily the final set

### Working hypothesis

RSGD records define which families/resources can potentially be generated under a biome/resource-generation configuration.

Runtime logic then selects a deterministic subset.

### Evidence

Changing relevant RSGD data changes possible outcomes.

### Open question

It is not yet known how much of the branch/family structure is encoded directly in RSGD/leveled-list data versus implemented in native code.

Status: strongly supported at a high level.

## H7 — Unique inorganic resources are endpoints of ordinary families

### Working hypothesis

The following unique resources should be treated as members/endpoints of their associated families rather than standalone families:

- Indicite → Aluminium
- Tasine → Nickel
- Vytinium → Uranium
- Aldumite → Chlorine
- Rothicite → Iron
- Veryl → Argon

### Evidence

Known unique-resource planets also contain the corresponding family root.

Treating Indicite or Vytinium as separate families creates violations of the observed `FamilyCount <= BiomeCount` constraint.

Status: strongly supported for the family model.

## H8 — The Creation Kit Apply Seed path contains or approaches the target algorithm

### Working hypothesis

The path beginning at:

```text
ResourceViewWidget::OnApplySeed
```

is close to the logic needed to reconstruct runtime resource allocation.

Known trace:

```text
ResourceViewWidget::OnApplySeed
    ↓
FUN_1431bc320
    ↓
FUN_140e457b0
    ↓
generic leveled-list machinery
```

### Why this matters

The Creation Kit must produce a resource preview from seed/configuration data, making this path a promising entry point for tracing where BIOM, RSGD, and RSCS data converge.

### Risk

The Creation Kit may wrap, simulate, or partially duplicate game-runtime logic rather than invoking the exact runtime path.

Status: promising investigative lead.

## H9 — SurveyAggregator is an oracle, not the allocator

### Working hypothesis

`SurveyAggregator` exposes final planet-wide resource results but consumes already-determined state rather than performing family-to-biome allocation.

### Usefulness

Even if it is downstream, it can serve as an authoritative oracle for testing candidate reconstructed algorithms over large numbers of planets.

Status: likely, not formally proven.

## Practical Planner Rule

Until the allocation algorithm is reconstructed, the planner can use the following conservative heuristic:

> Assume required resources from different ordinary inorganic families are not co-located within one normal biome.

Therefore the approximate minimum number of ordinary outposts required on one body is:

```text
number of distinct required resource families
```

This is a planning heuristic, not a statement that every family maps globally to exactly one biome.

Biome-boundary hunting should be treated as an exception rather than the default planning assumption.
