## Admission and paired observation

The retail adapter retains a verified Steam prelaunch client and checks an
identity-pinned log tail for an appended AppID/PID/full-image record. It joins
that record to the Windows process census, Steam parent, creation time,
ordinary token, session and account. Selection supplies no PID option. The
adapter opens the selected game with `PROCESS_QUERY_INFORMATION |
PROCESS_VM_READ` (`0x0410`), while client evidence uses process query and
`TOKEN_QUERY` metadata. Inherited handles, additional process rights and
debugger or thread-control APIs have no place in the read path. The simulator
uses the same acquisition code with an owned child and separately checks its
launch handle and exact creation epoch.

The adapter compares the image filename, file identity, binary hash, PE
headers, mapped extent and backing name. The reader handles legitimate
`ImageBase` relocation and compares four relocation-free windows at RVAs
`0x23FF660`, `0x5F7A9A`, `0x3832EE` and `0x779B16`. These cover the root,
reader, ordered key comparison and writer evidence respectively. The native
decoder follows the established published owner, registered component type,
index and separate FormID witnesses. Acquisition keeps the two bounded
collections, 25 ms gap, five-second window and structural limits. Each
collection rechecks the exact profile, process epoch and mapped image.

The controller consumes the single-use token before attempting acquisition.
It checks token and epoch, issuance and confirmation order, monotonic and
wall-clock consistency, and 30-second marker freshness. This measures the age
of the operator declaration, independent of the length of the game session.
The independent challenger demonstrated that a coherently backdated marker
could identify the correct process while claiming an observation before its
birth. The revised controller compares epoch creation FILETIME with the
operator timestamp. Live-style rehearsal and sealed replay exercise that
refusal. Failed attempts have no automatic retry.

The replay uses the original ordered read replies, logged identity and
bounded private Steam log evidence with tail, line and append hashes. It
revalidates the marker and input decision before comparing the result to the
receipt. Replay reproduces the evidence interpretation. It does not access
Windows processes or independently reacquire operational facts. The SHA-256
seal detects changes relative to the retained evidence and supplies no
signature of its author. An incomplete or contradictory receipt supplies no
qualified measurement.

Eligible zero results apply only to the sampled component and observation
window. Equal samples can miss ABA or capture a stable intermediate clear.
Readable words with unknown inputs remain conditional, with the official
verdict `STATE_INDETERMINATE`. These observations establish neither the
timing of allocator execution nor persistence or save serialization.
